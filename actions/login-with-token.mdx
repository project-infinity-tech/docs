**Login With Token** signs a user in by matching a token against the value stored for their email. It is how a user is authenticated when they click a magic link or an invite link, rather than by entering a password.

---

## What is Login With Token?

It is the **consume** half of a token-based auth flow. `Generate Secret Token` issues a token and emails it; `Login With Token` takes the token back when the user clicks the link, checks it against what is stored, and signs the user in if it matches.

It compares the token you give it against **exactly** what is stored — it does no hashing of its own. This one fact determines how you call it.

---

## Inputs

| **Input** | **Type** | **Notes** |
| --- | --- | --- |
| **email** | text | The user's email address. The link that carries the token must also carry the email, so both are available at consume time. |
| **token** | text | The token to match, in whatever form it was stored. |

Because `Login With Token` compares against exactly what is stored:

- If you stored the token **hashed** (the recommended pattern), **hash the incoming token before passing it here**.
- If you stored the token **raw**, pass it raw.

In other words: hash on consume if and only if you hashed on store. See [how to hash](/recipes/auth-flow-recipes#how-to-hash).

---

## Returns

On success, the action returns:

| **Field** | **Type** | **Meaning** |
| --- | --- | --- |
| **userId** | uuid | The id of the user who has just been signed in. |

On failure it returns no value — it raises a typed error. There is no `success` field on the payload.

<Note>
  **What you actually address in an expression.** Every step in Scram wraps its result in an envelope, so the declared output above is not what you reach directly. The envelope carries `value` (the action's own payload), `additional`, and `success`.

  ```text
  steps["<stepId>"].output.success          → true / false
  steps["<stepId>"].output.value.userId     → the signed-in user's id
  ```

  `steps["<stepId>"].output.userId` is the natural reading of the table above and resolves to undefined. Branch on the envelope's `success`; read the payload through `value`.
</Note>

## Errors

| **Code** | **When** |
| --- | --- |
| **Unauthorized** | The token does not match, has expired, has no expiry set, or has already been used. |
| **TooManyRequests** | Rate limit reached. |
| **ValidationFailure** | An input failed validation — for example a missing or empty email. |
| **UncategorisedError** | Anything else. |

<Warning>
  Handle `TooManyRequests` separately from the rest. The natural failure copy for a bad link — "request a new one" — is the wrong instruction for a rate-limited user, and following it makes the situation worse.
</Warning>

{/* VERIFY: only Unauthorized has been observed in testing. The conditions listed
    for TooManyRequests, ValidationFailure and UncategorisedError are inferred
    from the code names. A missing email param is the cheapest test and should
    confirm ValidationFailure. */}

## How it Works at Runtime

1. You pass the email and the token (hashed, if you stored it hashed).
2. The action looks up the user by email and compares the token against the stored value.
3. It checks `passwordResetTokenExpiresAt`. An expired timestamp is rejected — and so is a null one.
4. On a match, the user is signed in, **both token columns are cleared**, and the action returns `{ userId }`.
5. On no match — wrong, tampered, expired, or already used — it raises a typed error.

<Note>
  **The token is single-use, and the action enforces this itself.** A successful login sets `passwordResetToken` and `passwordResetTokenExpiresAt` to null, so replaying the same link fails. You do not need a step to clear them afterwards.
</Note>

<Note>
  **Run it in a Page Load workflow.** A failed step does not halt the workflow — execution continues to the next step — so you can branch on the result and render an error on the same page.
</Note>

{/* VERIFY: continue-on-error was observed in a Page Load workflow only. Not
    tested in button-triggered or reusable workflows. Do not generalise. */}

<Warning>
  **This action does not check `emailVerifiedAt`, and does not set it.** A user with an unverified email can sign in with a valid token — reasonably, since receiving the link proves inbox control. But the proof is not recorded, so the user stays unverified. If your app gates access on verification, check it yourself after the login step.
</Warning>

## Common Patterns

### Consuming a magic link

```text
Page Load workflow:
  Step 1: hash the token from the URL
  Step 2: Login With Token(email, hashed token)
  Step 3: If/Else on steps["<step2Id>"].output.success
            true  → navigate to the target path
            false → show the failure message
```

### Reading the result

```text
steps["<step2Id>"].output.success          → branch on this
steps["<step2Id>"].output.value.userId     → the signed-in user
```

---

## Important Constraints

- **Compares against exactly what is stored.** Hash before calling only if you hashed before storing.
- **Requires both email and token.** The link must carry both.
- **Failure raises rather than returning.** There is no `success` field on the payload — branch on the step envelope's `success`.
- **Does not verify email addresses.** It neither requires nor sets `emailVerifiedAt`.

---

## Relationship to Other Actions

- **Generate Secret Token** — issues the token this action consumes.
- **Set Password** — commonly follows for invite flows, letting a passwordless user set a password after first sign-in.

See [Auth flow recipes](/recipes/auth-flow-recipes) for complete flows.

---

In summary: `Login With Token` is the **consume** step of an email-link auth flow. It matches a token against stored state, enforces expiry and single use, and signs the user in — remember to hash on the way in if you hashed on the way out, and to branch on the step envelope rather than the payload.
